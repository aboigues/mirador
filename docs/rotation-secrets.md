# Rotation des secrets Mirador

**Motif** : le 2026-07-15, un fichier `infra/scaleway/.secrets.env.swp` (swap vim) a été
commité, puis purgé de l'historique avec `git-filter-repo` + force-push.

**La purge ne suffit pas.** Vérifié le 2026-07-16 : les anciens commits sont **toujours
servis par GitHub** (objets orphelins accessibles par leur SHA, non collectés
automatiquement), et le blob du swap reste **téléchargeable** via l'API. Il contient toutes
les clés en clair. Le dépôt est privé et sans fork, donc l'exposition se limite à qui a — ou
a eu — un accès en lecture ; mais tant que les valeurs sont valides, elles sont exploitables.

**Seule la rotation règle le problème.** Une fois les secrets tournés, le blob ne vaut plus
rien, qu'il soit encore accessible ou non.

**Mise à jour du 2026-09-24** : le blob n'était atteignable que par `refs/pull/17/head`,
une ref en lecture seule qu'un force-push ne peut pas réécrire. Accès vérifiés : aucun
collaborateur, fork, deploy key ou token fine-grained en dehors du propriétaire, seulement des
Apps de confiance. Le dépôt a été republié à neuf (seul `master`, dont l'historique ne
contient pas le blob) et l'ancien dépôt supprimé : les refs de PR et les objets orphelins
ont disparu avec lui. La rotation reste recommandée par hygiène.

## Portée

| Secret | Exposé | Ce qu'il ouvre |
|---|---|---|
| `ANTHROPIC_API_KEY` | ✅ | Facturation API Claude |
| `GITHUB_APP_PRIVATE_KEY` | ✅ | **Identité de la GitHub App** sur les dépôts de l'installation |
| `WEBHOOK_SECRET` | ✅ | Forger des webhooks signés → faire agir Mirador |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | ✅ | Bucket d'audit (`SCW0C45PRGYFEYX53AN8`, app IAM `mirador`) |
| `MNQ_ACCESS_KEY` / `MNQ_SECRET_KEY` | ✅ | File de messages (credential `mirador`, `39cdedeb`) |
| `SCW_ACCESS_KEY` / `SCW_SECRET_KEY` / `SCW_PROJECT_ID` | ❌ | **Non exposées** — créées après (PR #14). Ne pas y toucher. |

Le plus grave est la **clé privée de la GitHub App** : elle permet de s'authentifier comme
Mirador sur les dépôts de l'installation 145689603, avec droits d'écriture (PR, issues).
L'installation est restreinte aux seuls dépôts surveillés (2026-09-24 ; 38 auparavant).

## Principe

Pour chaque secret : **créer le nouveau → le valider localement → mettre à jour le Secret
GitHub → lancer `deploy-config.yml` → vérifier → seulement alors révoquer l'ancien.**

Valider *avant* de déployer évite de découvrir une clé fautive en production. Révoquer
*après* évite toute coupure.

⚠️ **Deux pièges à ne pas rater :**

1. **Ne PAS supprimer la credential MnQ auto-générée** (`b4495940`, « Auto-generated by
   serverless function for trigger… Please do not delete »). C'est celle que le trigger
   Scaleway utilise pour **lire** la file. Elle n'est pas exposée. La supprimer casse la
   chaîne webhook → traitement. Seule la credential nommée `mirador` (`39cdedeb`) est à
   tourner.
2. **Aucun déploiement en local** : la config passe par `deploy-config.yml`
   (Actions → *Configuration Scaleway* → Run workflow). Voir le README.

## 1. Clé privée de la GitHub App

**Sans coupure** : une App accepte plusieurs clés privées simultanément.

1. GitHub → Settings → Developer settings → GitHub Apps → **Mirador** → *Private keys* →
   **Generate a private key**. Un `.pem` est téléchargé.
2. Valider la nouvelle clé **avant** de déployer :

```bash
GITHUB_APP_ID=4265528 GITHUB_APP_PRIVATE_KEY="$(cat ~/Downloads/mirador.*.private-key.pem)" \
.venv/bin/python - <<'PY'
import asyncio, os, sys
sys.path.insert(0, ".")
from src.infrastructure.github.app_auth import GitHubAppAuth
async def main():
    auth = GitHubAppAuth(os.environ["GITHUB_APP_ID"], os.environ["GITHUB_APP_PRIVATE_KEY"])
    token = await auth.obtenir_token_installation(145689603)
    print("✓ token d'installation obtenu :", token[:8] + "…")
asyncio.run(main())
PY
```

3. Mettre à jour le Secret GitHub **`APP_PRIVATE_KEY`** (le préfixe `GITHUB_` est réservé).
   Coller le PEM **tel quel** — les Secrets GitHub acceptent le multiligne, et `app_auth.py`
   normalise aussi la forme `\n` échappés.
4. Lancer **`deploy-config.yml`**.
5. Vérifier : les deux fonctions `ready`, 7/7 secrets (le workflow l'affiche en fin de job).
6. **Puis** supprimer l'ancienne clé dans *Private keys* (bouton *Delete*).

## 2. Clé API Anthropic

1. [console.anthropic.com](https://console.anthropic.com) → Settings → API keys → **Create key**.
2. Valider (appel gratuit, ne consomme pas de tokens facturables) :

```bash

print("✓ clé valide —", r.input_tokens, "tokens")
PY
```

3. Mettre à jour le Secret **`ANTHROPIC_API_KEY`** → lancer `deploy-config.yml`.
4. **Puis** révoquer l'ancienne clé dans la console.

## 4. Credentials MnQ (file de messages)

La credential exposée est **`mirador` (`39cdedeb-6d47-4cee-8e9a-1e37710501ba`)**.

⚠️ **Ne pas toucher à `b4495940`** (auto-générée, utilisée par le trigger pour lire la file).

Elle a aujourd'hui `can_publish` + `can_receive` + `can_manage`. Or le runtime ne fait qu'un
`send_message` (`webhook.py:39`) : **`can_publish` seul suffit**. La rotation est l'occasion
d'appliquer le moindre privilège.

```bash
scw mnq sqs create-credentials \
  name=mirador-runtime \
  project-id=4135267b-fd5a-4079-b716-8b24240deabd \
  region=fr-par \
  permissions.can-publish=true \
  permissions.can-receive=false \
  permissions.can-manage=false \
  --profile telemach
```

Valider :

```bash
AWS_ACCESS_KEY_ID=NOUVELLE_MNQ_ACCESS AWS_SECRET_ACCESS_KEY=NOUVELLE_MNQ_SECRET \
.venv/bin/python - <<'PY'
import boto3
c = boto3.client("sqs", endpoint_url="https://sqs.mnq.fr-par.scaleway.com", region_name="fr-par")
c.send_message(QueueUrl="https://sqs.mnq.fr-par.scaleway.com/project-4135267b-fd5a-4079-b716-8b24240deabd/mirador-webhooks",
               MessageBody='{"type":"ping-rotation"}')
print("✓ publication OK (message ignoré par le pipeline : type inconnu)")
PY
```

Mettre à jour **`MNQ_ACCESS_KEY`** / **`MNQ_SECRET_KEY`** → `deploy-config.yml` → vérifier →
**puis** supprimer l'ancienne :

```bash
scw mnq sqs delete-credentials 39cdedeb-6d47-4cee-8e9a-1e37710501ba region=fr-par --profile telemach
```

> Note : `infra/scaleway/purger_queues.py` et `creer_queues.py` ont besoin de `can_manage`.
> Si tu t'en sers, crée une credential d'administration **séparée**, à garder hors du runtime.

## 5. `WEBHOOK_SECRET` — à faire en dernier

C'est **le seul avec une fenêtre de coupure** : GitHub signe avec l'ancien secret tant que
l'App n'est pas mise à jour, et Mirador valide avec le nouveau dès le déploiement. Entre les
deux, les webhooks repartent en **403**.

1. Générer : `openssl rand -hex 32`
2. Mettre à jour le Secret GitHub **`WEBHOOK_SECRET`** → lancer `deploy-config.yml` → attendre
   que les deux fonctions soient `ready`.
3. **Immédiatement après** : GitHub App **Mirador** → *Webhook secret* → coller la même valeur
   → *Save*.
4. Rattraper les livraisons perdues : App → *Advanced* → *Recent Deliveries* → **Redeliver**
   celles en 403 pendant la fenêtre.

Faire l'opération à un moment calme (pas pendant un scan hebdomadaire, cf. crons du lundi
matin), pour réduire la fenêtre à néant.

## 7. Vérification finale

Le seul test qui vaille est un bout en bout réel : déclencher un run en échec sur `k8t` et
vérifier qu'une Issue s'ouvre avec une proposition. Il exerce d'un coup la clé App (auth +
logs), le `WEBHOOK_SECRET` (HMAC), MnQ (publication + trigger), Anthropic (proposition) et
Object Storage (audit).

Si l'Issue s'ouvre en affichant « Analyse indisponible », tout marche **sauf** la clé
Anthropic (cf. la résilience de la PR #19).
